# Foundation phase — durable jobs, Postgres, auth & multi-tenancy

This phase implements the blueprint's core foundation items that were
deliberately deferred during the repository rescue. The in-memory job dict and
daemon threads are gone; the system now has a durable, multi-tenant backbone.

## What was built

### 1. Postgres system-of-record (`backend/db/`)
- SQLAlchemy 2.0 models: `Organization`, `User`, `Membership`, `Project`,
  `Job`, `ChapterResult`, `JobAttempt`.
- Backend-agnostic `GUID` type (native `uuid` on Postgres, `String(36)` on SQLite).
- Alembic migrations (`backend/migrations/`) with an autogenerated initial
  schema; `alembic upgrade head` / `downgrade base` round-trip verified.
- Lazy engine + `session_scope()` transactional helper. `DATABASE_URL` selects
  the backend; `postgres://` / `postgresql://` are normalized to the psycopg driver.

### 2. Durable job queue + worker (`backend/jobs/`, `backend/worker.py`)
- Jobs are durable rows with a proper state machine
  (`queued → running → succeeded|failed|canceled`) plus queue columns.
- `claim_next_job` uses `SELECT ... FOR UPDATE SKIP LOCKED` on Postgres so
  multiple workers never claim the same job and never block each other;
  degrades to an ordered SELECT on SQLite (single-worker dev).
- **Restart safety:** `recover_orphans` requeues jobs whose worker died (stale
  lock), on startup and periodically. Per-chapter progress is committed as it
  runs, so a resumed job skips already-finished chapters.
- **Retry/backoff:** failures requeue with a delay until `max_attempts`, then
  fail permanently. Every attempt is recorded in `job_attempts` for audit.
- **Cancellation:** cooperative — queued jobs cancel immediately; running jobs
  stop at the next heartbeat.
- The pipeline (`jobs/pipeline.py`) is the old synthesis/QC/assembly logic,
  decoupled from the web layer and driven by a `Job` row.

### 3. Auth & multi-tenancy (`backend/auth/`)
- bcrypt password hashing; JWT access tokens (`JWT_SECRET`, required in prod).
- `signup` creates a personal organization and makes the user its owner.
- `require_auth` guard resolves the current user + active org from the bearer
  token and verifies membership on every request.
- **Ownership:** `_get_owned_job` + `resolve_org` ensure a job/task id no longer
  authorizes access — a non-member gets **403**, and we return 403 (not 404) so
  we don't even confirm a resource exists to outsiders.

### 4. API rewrite (`backend/app.py`)
- Request-scoped DB session via `before_request`/`teardown_request`.
- New auth endpoints; `/api/synthesize` now creates a `Project` and **enqueues**
  a durable job instead of spawning a thread; added `/api/jobs`,
  `/api/jobs/<id>/cancel`; `/api/health` checks DB connectivity.
- All work endpoints authenticated and org-scoped.

### 5. Frontend (`frontend/src/`)
- Axios interceptor attaches the JWT; `AuthGate` provides login/signup and gates
  the app; header shows a sign-out control.

### 6. Ops (`docker-compose.yml`, `backend/Dockerfile`, `entrypoint.sh`)
- Compose adds `db` (Postgres 16) and a `worker` service sharing the data volume;
  the backend runs migrations on start via the entrypoint. Workers scale
  horizontally (`--scale worker=N`).

## Verification

Run in the sandbox (SQLite) and confirmed green:

- `pytest -q` → **16 passed, 1 skipped** (the skipped one is the Postgres-only
  `FOR UPDATE SKIP LOCKED` concurrency test — it runs in CI/against Postgres).
- `ruff check .` → **All checks passed**.
- Alembic `upgrade head` → `downgrade base` → `upgrade head` round-trip → OK.
- Frontend `tsc --noEmit` → pass; `vite build` → built; `eslint` → clean.

Test coverage highlights:
- job enqueue → claim → complete, with double-claim prevention;
- end-to-end worker run producing MP3 + M4B (stubbed provider/ffmpeg);
- retry/backoff then permanent failure with attempt records;
- orphan recovery requeues a dead worker's job;
- restart resumes already-completed chapters;
- queued-job cancellation;
- auth signup/login (+ duplicate + weak-password rejection);
- **cross-org isolation**: non-members get 403 on read/download/cancel, and job
  listings are scoped per org.

## Note on the sandbox

A real Postgres server could not be run in this build sandbox (no root, no
bundled-Postgres wheel for the ARM image), so the automated suite here runs on
SQLite and the one concurrency test that needs true row-locking is auto-skipped.
The code is written Postgres-first; point `DATABASE_URL` at Postgres (as the
docker-compose and CI do) to exercise it fully — that test is ready to run there.
